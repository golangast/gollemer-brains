# Data formats

The interface of gollemer-brains is two files. A program built on the
brains reads meanings from a **declarations file** and learns them from
a **training-pairs file**; everything else — the matcher, the
classifier, the trained brain on disk — is mechanism behind those two
files, and can change without the files changing. This document is the
contract for both files, plus the trained artifacts the tools write.

## The declarations file

One JSON object: an optional `comment` (the file explaining itself to
its owner) and `scripts`, the declarations in file order.

```json
{
  "comment": "what this file is, in the owner's words",
  "scripts": [
    {
      "name": "copy",
      "command": "./copy.sh",
      "description": "copy files from one folder to another",
      "slots": ["from", "to"],
      "examples": ["copy the photos from jim to jake"]
    }
  ]
}
```

Each declaration:

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | The meaning's name. Unique in the file. This is the value a program switches on. |
| `command` | yes, unless `steps` | The command line bound to the meaning. Argument values are appended to it in `slots` order. |
| `description` | yes | What the meaning does, in plain words. **This is the match surface**: what a person types is matched against the description (and the name), so write it the way the owner would say it. |
| `slots` | no | The argument names the command takes, in the order they are appended to the command line. Names within one declaration are unique. Slot values are seated from the typed line: lifted verbatim where the line anchors them (a `from` slot seats the words after "from"), generated by the extractor brain where it does not. |
| `examples` | no | A few sentences in the owner's own words that mean this declaration. They widen what the matcher recognises; the description alone is enough. |
| `stage` | no | Plan metadata: a rough order tag (`inspect`, `prepare`, `execute`, `verify`, `cleanup`) saying where in a multi-step job this command belongs. Ignored by the matcher. |
| `after` | no | Plan metadata: names of other declarations that should run before this one when both appear in a plan. Ignored by the matcher. |
| `acts_on` | no | Plan metadata: a hint about what kind of thing the command acts on (`file`, `tests`, `repo`, `logs`, …), so plan steps can share context. Ignored by the matcher. |
| `needs` | no | Concepts that should run *earlier* than this one in a job — a relation, not an ordering the plan enforces. When a plan renders, a need that is absent or sitting later earns a printed note. Ignored by the matcher. |
| `steps` | no | Makes the entry a **routine** instead of a script: a list of segment texts, each the kind of line that would match one of the registry's commands. A routine has no `command` of its own; a want that matches it expands into a plan of its steps. A declaration carries `steps` or `command`, never both. |
| `relations` | no | The typed relationships this command stands in: a list of `{name, slot, target}`. Names come from a fixed vocabulary — `moves_from`/`moves_to` (one edge, read either way; the value in `slot` must be a place), `targets`, `cancels`, `invokes`, `requires` (whose far side is a command named in `target`), `contains`/`part_of`. Only *stated* relations are validated: a seated value that does not fit its relation's range is **reported** in the reading, never dropped or reseated. A declaration that states none still implies the obvious ones from its shape (`from`/`to` slots, its `needs`) — teach-by-declaration writes those in for you. |
| `slot_types` | no | The value type of individual slots: a map from slot name to one of `person`, `folder`, `file`, `time`, `place`, `object`, `command`, `text`, `number`. A seated value carries its slot's type for the session, and relation ranges are checked against it. |
| `object_type` | no | The type of the thing this command acts on as a whole (its `acts_on`, typed, from the same vocabulary as `slot_types`). A declared property of the concept — an addition to its examples, never a replacement for them. |

Validation (a malformed file is an error that names the problem, never
a silent half-read): every declaration has a name, names are unique,
every declaration has a description, a non-routine has a command, a
routine has no command and no empty steps, and slot names within a
declaration are unique.

Matching notes a builder relies on:

- Matching is lexical and runtime: a declaration added to the file is
  matchable on the next line typed, with no retraining.
- Word kinship comes from a fixed synonym table in the matcher
  (cousins): a typed word that is a cousin of a description word
  counts, at reduced weight. The families are deliberately narrow —
  in particular, words an owner would treat as different things
  (file/folder) are not cousins of each other.
- A line matches only when it clears all the matcher's bars —
  a score threshold, a matched-mass floor, at least two matched
  content words, and a margin over the runner-up. Below any bar the
  matcher abstains rather than guess.

## The training-pairs file

JSONL: one JSON object per line. Blank lines are skipped. A malformed
line is an error that names its line number.

```json
{"input": "turn off the lights", "output": "Turning the lights off.", "intent": "lights_off", "kind": "make"}
{"input": "lights on please", "intent": "lights_on", "kind": "make"}
```

| Field | Required | Meaning |
|---|---|---|
| `input` | yes | A line a person might type. Empty is an error. |
| `output` | yes, unless `intent` is present | The reply or result the line should produce. For command/extractor corpora the output is the argument values, in slot order, space-separated (`{"input": "copy the archive from adam to winter", "output": "adam winter"}`). |
| `intent` | no | The meaning label this line belongs to. A row with an `intent` but no `output` is a **label-only row**: a pure meaning example. |
| `kind` | no | The broad family the row's `intent` belongs to — the meaning's neighbourhood (`make`, `schedule`, `talk`, …). A kind only ever annotates an intent; it never replaces one. |
| `subkind` | no | A family *within* the row's kind (`explain` inside `find`): the tree runs kind → sub-kind → concept, three levels at most. A sub-kind belongs to exactly one kind and one label to exactly one sub-kind — violations are data errors, named like kind conflicts. Sub-kinds inherit their kind's fallback candidates and disjointness pairs; the fallback's walk climbs through them, and ambiguity at kind level can be resolved by composition inside the narrow read's sub-kind. |

Further fields are ignored by the loaders, so a file carrying extra
annotation still loads.

Who learns what from a pairs file:

- The **intent classifier** trains on every row that carries an
  `intent`, with or without an `output`. It needs at least two labels
  to learn anything.
- The **seq2seq brain** trains on rows that carry an `output`;
  label-only rows teach it nothing and are skipped.
- The **extractor** (the generic-command brain) trains on pairs whose
  `output` is the argument values of the input's sentence shape.

Kind conventions:

- **One label, one kind.** A label whose rows carry two different
  kinds is a data error, reported with the label and both kinds
  named — a meaning belongs to one neighbourhood.
- Kinds are free-form strings; a corpus defines its own set. The
  shipped chat corpus uses nine — `make`, `remove`, `show`,
  `schedule`, `play`, `communicate`, `find`, `travel`, `talk` — and
  the triage example in `examples/triage` uses its own five. A label
  whose rows carry no kind simply has no neighbourhood.
- **Label naming is load-bearing.** Labels written as
  `action_object` (`create_file`, `explain_goroutine`) factorize:
  when the classifier abstains on a line, a fallback can compose a
  read from the predicted kind plus the object words the line itself
  carries — adopted only when exactly one label in that kind matches
  the line's whole object set. Single-token labels (`greeting`)
  cannot be composed this way.

## The trained artifacts

Training (`go run ./cmd/train -data <pairs> -out <brain.gob>`, or
`go run ./cmd/train -dir <folder>` for a whole domain folder) writes:

- **`<out>`** — the trained seq2seq brain (a gob). Written once, at
  the end of the run, from the best weights seen.
- **`<out>.intents.json`** — the intent classifier sidecar, written
  when the data carried `intent` fields: the labels, the feature
  scheme, the weights, and the label→kind map. A brain and its
  sidecar travel together; loading a brain picks its sidecar up.
- **`<out>.ckpt` / `<out>.latest`** (+ JSON sidecars) — training
  checkpoints, written during a run so a killed run can resume with
  `-resume` instead of starting over. They are working state, not
  artifacts to ship.

## When a line misreads

Every reading carries its provenance: which words reached a
declaration and how (a defining word, an example word, a cousin link,
a typo repair), which rule composed or withheld a read. In
`examples/customcmd` that is the `-inspect` flag; through the
`interpret` package it is a Reading's `Trace` and the `Explain`
method. The fix for a misread is a declaration or a training row —
the provenance names which one.
